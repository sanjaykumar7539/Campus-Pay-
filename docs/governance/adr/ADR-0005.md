# ADR-0005: Campus Commerce Ownership under the Merchant Module

**ADR ID:** ADR-0005  
**Title:** Catalog, Order, OrderItem and Fulfillment are owned by Merchant  
**Status:** Proposed (pending approval)  
**Date:** 21 September 2026  
**Decision Makers:** CampusPay Engineering Team

---

# Context

The approved architecture has no Order/Catalog entities. The Operating Model requires merchant-specific menus (AVAILABLE / SOLD_OUT / UNAVAILABLE), server-authoritative orders, price snapshots and merchant fulfillment (PAID → PREPARING → READY → COLLECTED). Merchant "owns merchant functionality"; Payments owns merchant financial transactions.

# Decision

1. **Merchant** owns Category, Product (price, availability), Order, OrderItem (unit-price snapshot), Fulfillment and staff assignment. No new module folder is created.
2. **Payments** owns Payment and Receipt. Order and Payment stay separate state machines; Payment stores `order_id`, Order never stores a payment id.
3. Dependency changes (ADR-0003 Rule 5): Merchant → Users, Devices, Audit; Payments → Auth, Users, Merchant, Wallet, Audit; Wallet → Users, Ledger, Audit; Auth → Users, Institutions, Audit; Reports → Users, Wallet, Merchant, Payments, Devices, Ledger, Audit. All acyclic; Merchant never depends on Wallet, Ledger or Payments, so merchant staff cannot alter financial state.
4. Order status (CREATED, PAID, CANCELLED) is independent of Payment (INITIATED, COMPLETED, FAILED), Receipt (ISSUED) and Fulfillment (PAID, PREPARING, READY, COLLECTED).
5. Menu-change authority (MG-08), price change on existing carts (MG-09) and paid-order cancellation (MG-15) remain OPEN: menu roles are configuration; paid-order cancellation is refused.

# Consequences

Simple ownership, no cycles, enforced by `tests/test_architecture_boundaries.py`. Merchant module grows; a Commerce module can be extracted later by a new ADR.
