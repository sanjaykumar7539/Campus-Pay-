# ADR-0003: Backend Module Structure and Naming

**ADR ID:** ADR-0003
**Title:** Backend Module Structure and Naming
**Status:** Accepted
**Date:** 27 July 2026
**Decision Makers:** CampusPay Engineering Team

---

# Context

ADR-0002 established that CampusPay shall be implemented as a Modular Monolith, organised around business capabilities defined in `ARCHITECTURE.md` §7 (Module Architecture).

During backend project structure design, two gaps were identified between the existing repository scaffold and the documented architecture:

1. **Missing Institution module.** `ARCHITECTURE.md` §7.3 defines Institution as a required business module — the tenant root that every other module ultimately depends on, per ADR-0001's tenant-centric design principle. The repository scaffold's `backend/modules/` directory did not include an `institutions/` folder.

2. **Naming mismatch for the Campus User module.** `ARCHITECTURE.md` §7.4 and `governance/terminology.md` define a single **Campus User** module that owns Students, Faculty Members, and Administrative Staff as a unified concept. The repository scaffold instead contained a folder named `students/`, which both undershoots the module's documented scope (it owns more than students) and conflicts with the canonical terminology ("Campus User" is the reserved collective term; `terminology.md`'s Reserved Terminology table explicitly lists "User, Member" as terms to avoid in favour of more precise names, and the module boundary in `ARCHITECTURE.md` is broader than "students" alone).

Because `claude.md` prohibits inventing modules, renaming directories, or removing existing modules without explicit approval, these gaps were raised for a decision rather than silently resolved during structure design.

This ADR formalises the resolution and establishes durable rules for how backend module folders may be added, named, or renamed in the future.

---

# Decision

The following backend module structure decisions are **approved and canonical**:

1. **`backend/modules/institutions/` is added** as a new module folder, implementing the Institution module defined in `ARCHITECTURE.md` §7.3.

2. **`backend/modules/students/` is renamed to `backend/modules/users/`**, implementing the Campus User module defined in `ARCHITECTURE.md` §7.4. The folder name `users` is chosen as the closest filesystem-safe rendering of "Campus User"; the module continues to own Student, Faculty, and Administrative Staff entities exactly as scoped in `ARCHITECTURE.md` — this is a naming correction only, not a scope change.

3. This structure — as set out in the "Canonical Backend Module Structure" section below — is the **authoritative backend layout for CampusPay going forward**. All future backend development shall conform to it.

No other module folders are added, removed, or renamed by this decision.

---

# Canonical Backend Module Structure

```
backend/modules/
├── institutions/     # Institution (tenant) module — ARCHITECTURE.md §7.3
├── auth/              # Authentication module — ARCHITECTURE.md §7.2
├── users/             # Campus User module (Student/Faculty/Admin) — ARCHITECTURE.md §7.4
├── wallets/           # Wallet module — ARCHITECTURE.md §7.5
├── payments/          # Payments module — ARCHITECTURE.md §7.6
├── merchants/         # Merchant module — ARCHITECTURE.md §7.7
├── attendance/        # Attendance module — ARCHITECTURE.md §7.8
├── notifications/     # Notifications module — ARCHITECTURE.md §7.9
├── reports/           # Reporting module — ARCHITECTURE.md §7.10
├── devices/           # Device module — ARCHITECTURE.md §7.11
└── audit/             # Audit (cross-cutting) — ARCHITECTURE.md §9.5
```

This list now matches `ARCHITECTURE.md` §7 exactly: eleven modules, each with a one-to-one correspondence between a documented business capability and a physical `backend/modules/<name>/` folder.

---

# Rationale

## 1. One-to-One Correspondence with Documented Architecture

`ARCHITECTURE.md` §7.12 (Module Ownership Principles) requires that every business entity have exactly one owning module, and §8.2 Rule 1 requires the same at the architectural level. A repository structure that omits a documented module (Institution) or mislabels one (Students vs. Campus User) breaks this correspondence and creates ambiguity about where new code belongs.

## 2. Institution as Tenant Root Must Be Physically Represented

ADR-0001 establishes Institution as the root of tenant ownership — every business record belongs to exactly one Institution. The Module Dependency Matrix in `ARCHITECTURE.md` §8.3 lists Institution with no dependencies and multiple modules (Campus User, Wallet, Merchant, Device) depending on it. A backend structure without an `institutions/` folder has no home for this foundational entity, forcing institution logic to be improvised inside another module — a direct violation of Rule 1 (Module Ownership) and Rule 4 (Persistence Isolation).

## 3. Terminology Consistency

`terminology.md` establishes Campus User as the single official collective term and explicitly reserves it over alternatives like "User" or "Member" in isolation. Naming the folder `users/` is accepted as a pragmatic, filesystem-conventional shorthand for "Campus User" (matching common FastAPI/Django project conventions), while the module's owned entities, business rules, and documentation continue to use the full terminology from `terminology.md`. The folder `students/` was rejected because it named only one of the three personas (Student, Faculty, Administrative Staff) the module is documented to own, which would mislead contributors about the module's actual scope.

## 4. Prevents Silent Architectural Drift

`claude.md` requires that any conflict between the documentation and the repository be surfaced and resolved explicitly rather than papered over. Recording this as an ADR — rather than a casual folder rename — ensures the decision is traceable, reviewable, and binding on future contributors and AI-assisted code generation alike.

# Alternatives Considered

## Alternative 1 — Leave `students/` As-Is, Add Institution Only

### Advantages
- Smaller diff against the existing scaffold
- Avoids a rename

### Disadvantages
- Perpetuates a folder name that undersells the module's documented scope (Student + Faculty + Administrative Staff)
- Contributors unfamiliar with `ARCHITECTURE.md` §7.4 could reasonably (and incorrectly) place Faculty or Admin logic in a different, ad hoc location
- Creates a permanent naming inconsistency between code and terminology documentation

**Decision:** Rejected

---

## Alternative 2 — Fold Institution Logic into the Campus User Module

Treat Institution as a sub-concern of Campus User rather than a standalone module.

### Advantages
- Fewer top-level module folders

### Disadvantages
- Directly contradicts `ARCHITECTURE.md` §7.3, which defines Institution as an independent module and the tenant root
- Violates Module Ownership (§7.12) and would tangle tenant lifecycle logic with user lifecycle logic
- Breaks the documented Module Dependency Matrix, which models Institution as a zero-dependency module that others depend on, not a component of Campus User

**Decision:** Rejected

---

## Alternative 3 — Add `institutions/`, Rename `students/` to `users/`

Bring the repository structure into exact 1:1 alignment with `ARCHITECTURE.md` §7.

### Advantages
- Full correspondence between documented modules and physical folders
- Terminology-consistent module scope
- No ambiguity for future module additions or AI-assisted code generation

### Disadvantages
- Requires a rename, which `claude.md` normally restricts — mitigated here because the rename is explicitly approved via this ADR rather than performed unilaterally

**Decision:** Accepted

# Architectural Rules Governing Future Module Additions and Renames

This ADR establishes the following standing rules for the lifetime of the CampusPay backend.

## Rule 1 — Every Module Must Trace to `ARCHITECTURE.md` §7

No new folder may be added under `backend/modules/` unless it corresponds to a business module explicitly documented in `ARCHITECTURE.md` §7, or a new module is first introduced there via its own ADR (per `ARCHITECTURE.md` §16.2, AC-010 — ADR Governance).

## Rule 2 — No Silent Renames

A module folder shall never be renamed without an accompanying ADR recording the rationale, consistent with `claude.md`'s "never rename modules... without approval" constraint. This ADR itself is the precedent and template for how such a rename is proposed and approved.

## Rule 3 — Folder Name Must Not Contradict `terminology.md`

Where a documented module's business name (e.g., "Campus User") cannot be used verbatim as a folder name for technical reasons (pluralisation, filesystem conventions, framework idioms), the closest unambiguous derivative shall be used, and the mapping shall be recorded explicitly (as in this ADR) so the connection between code and terminology is never left implicit.

## Rule 4 — One Module, One Owner, One Folder

Consistent with `ARCHITECTURE.md` §7.12 Principle 1 and §8.2 Rule 1: each business entity is owned by exactly one module, and each module maps to exactly one `backend/modules/<name>/` folder. No entity's persistence or business rules may be split across two folders, and no folder may own entities documented as belonging to another module.

## Rule 5 — Dependency Direction Must Match §8.3 and §8.4

Any new module's declared dependencies (as reflected in its internal imports of other modules' service interfaces) must match the direction and content of the Module Dependency Matrix in `ARCHITECTURE.md` §8.3. If a new module requires a dependency not yet reflected in that matrix, the matrix must be updated via an ADR or an approved revision to `ARCHITECTURE.md` before implementation proceeds.

## Rule 6 — Structural Changes Require an ADR; Code Changes Do Not

Adding, removing, or renaming a top-level module folder is an architectural change and requires an ADR under this rule set. Ordinary code changes within an already-approved module folder (adding a service function, a new endpoint, a new field) do not require a new ADR, provided they don't alter module ownership or cross-module dependencies.

# Consequences

## Positive

- Backend folder structure now has exact 1:1 correspondence with `ARCHITECTURE.md` §7's documented modules
- Institution, as the tenant root, has an explicit, unambiguous home consistent with ADR-0001
- Campus User module naming no longer undersells its documented scope
- Future module additions and renames have a clear, repeatable governance process
- Reduces risk of architectural drift during AI-assisted or human development

## Negative

- One rename (`students/` → `users/`) must be carried out against the existing scaffold before module implementation begins
- Slightly larger module count (11 folders) to onboard new contributors to, though this matches documentation already in place

These trade-offs are considered acceptable in exchange for structural accuracy and long-term governance clarity.
