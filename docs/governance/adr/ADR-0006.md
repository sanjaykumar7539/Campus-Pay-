# ADR-0006: Order-Driven Purchase with 4-Digit PIN Authorization

**ADR ID:** ADR-0006  
**Title:** Payment authorization, idempotency and concurrency model  
**Status:** Proposed (pending approval)  
**Date:** 21 September 2026  
**Decision Makers:** CampusPay Engineering Team

---

# Context

The Operating Model separates Identity → Authentication → Payment Authorization and requires a 4-digit PIN for purchases. Identity mechanism (MG-02), PIN lockout/reset/unlock (MG-01) and network-failure behaviour (MG-13) are OPEN. The MVP paid a client-supplied amount with no PIN, no lock and a globally unique payment reference.

# Decision

1. **Authentication** owns the PIN credential (bcrypt, optional server-side pepper); Campus User owns identity; Payments coordinates. Identity is an abstraction (`users/identity.py`, only `CAMPUS_ID` registered).
2. Canonical flow `POST /orders/{id}/pay`: lock order → idempotency → validate → verify PIN → Payment INITIATED → Wallet debit (ledger PURCHASE first) → order PAID + Fulfillment → Payment COMPLETED → commit → digital Receipt (own transaction, idempotent). The payable amount is the server-derived order total.
3. Idempotency: `Idempotency-Key` unique per institution; replay returns the original result. DB backstops: partial unique index (one COMPLETED payment per order), unique ledger reference and per-customer ledger sequence. Row locks (order, wallet) serialize on PostgreSQL; SQLite serialises writers and is not evidence of production safety.
4. PIN failures are counted and audited and committed independently of the refused payment. Lockout threshold/duration are configuration with **no default** (both or neither); unset means count-only. Unlock authority and reset policy are OPEN: PIN provisioning is a provisional admin/demo mechanism and does not clear locks.
5. The MVP manual-amount endpoint remains only as a **deprecated**, flag-gated (`CAMPUSPAY_LEGACY_MANUAL_PAYMENT`) compatibility path through the same purchase core (PIN, tenant scope, ledger, idempotency all apply).

# Consequences

Correct-by-construction duplicate and race handling; receipt failure cannot reverse a debit. Open policies are configuration or explicit refusals, not invented rules.
